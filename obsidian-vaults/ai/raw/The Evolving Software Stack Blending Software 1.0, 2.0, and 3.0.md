In late 2017, [Andrej Karpathy coined the term Software 2.0](https://karpathy.medium.com/software-2-0-a64152b37c35) to describe software whose behavior is learned from data rather than explicitly written as code. In June 2025, he coined **Software 3.0**, arguing that large language models had turned neural networks into something we can now “ *program* ” directly in natural language.

He described LLMs as a new kind of operating system, a platform on top of which software can be written in English. Since then, that framing has only become more compelling as LLMs and agents have improved at an extraordinary pace.

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*-_IrhzGXAj13lz7gIZGhPA.png)

In his June 2025 talk, he framed LLMs this way: https://youtu.be/LCEmiRjPEtQ?t=614

This framing focuses primarily on the process of building, or how the system is constructed. The **Software 1.0** approach requires writing code where the business rules, algorithms, and logic of a system are explicitly specified. Regardless of who wrote the code, it is still crafted procedurally: a sequence of instructions laid out by an intelligence for the computer to execute.

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*EnKIGrZdtUVsEuTR2_9-mA.png)

The **Software 2.0** approach is largely the domain of data scientists. Instead of hand-authoring logic, the task becomes curating datasets, defining objectives, and shaping training pipelines. The product leaves the realm of human readability and is instead learned, or grown, into the weights of a model.

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*N4TfXGKBjSYK1mOCe_w53g.png)

LLMs themselves are built through these **Software 2.0** techniques, trained on massive datasets with expensive training runs, but they also enable a third way of crafting systems. With **Software 3.0**, the builder’s primary raw material is no longer code or training data, but language itself. Execution is not formally specified in code, nor is it learned into weights for each individual application. It is conveyed through natural language, making it accessible to effectively everyone.

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*FJXsjxeRlfASGKTKcBKlnA.png)

## The Basic Building Blocks

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*MhwFOMNN8AohtV1AGm5qeg.png)

Pure **Software 1.0** systems represent the largest fraction of the software you interact with each day. From the firmware running on your microwave to the web server that served this article, this way of building software is not going anywhere. If anything, more **Software 1.0** is being produced now than ever before. What has changed is not the form of the software, but who is producing it. Increasingly, that code is being generated by AI coding agents rather than written line-by-line by humans, yet it remains **Software 1.0** all the same: explicit, procedural logic specified for a machine to execute.

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*CtLq9oHGdDc_AsB0DB8hCQ.png)

**Software 2.0** has not become a mainstream skill for the average developer. Training machine learning models is still challenging, dependent on large, high-quality datasets and the specialized expertise required to shape, train, and evaluate them effectively.

At the same time, outside of foundation models and the wave of fine-tuning built around them, the role of narrow machine learning systems in language and vision appears to be shrinking. Many use cases that once justified training a dedicated model can now be handled well enough, and often more flexibly and with higher quality, by an LLM. Even so, **Software 2.0** is far from obsolete. In domain-specific settings, where specialized datasets still create real advantages, narrower models remain relevant and can still be the more performant option.

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*XH9byJpw587nPCt3g7DH0g.png)

In their raw form, LLMs provide a new kind of building block: general-purpose cognition that can be directed toward a wide range of problems. What makes this shift notable is that it can be steered through natural language. If you want a summary, a translation, or a revision of a document, you do not need to write a program or train a model for that specific task. You can simply ask.

That, in essence, is **Software 3.0**. The model provides the cognitive engine, and language becomes the interface for shaping its behavior. Once you move beyond one-off interactions and begin combining these capabilities into larger systems, you start to enter the world of agents, which is where we will turn next.

## Putting the Pieces Together

There are multiple ways to combine these different types of systems to solve different kinds of problems, each with its own advantages and disadvantages. What matters is not just understanding **Software 1.0**, **2.0**, and **3.0** on their own, but understanding how they fit together. These patterns are where things start to get interesting.

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*kpCJyH1t_SLrQCKBFkQk4w.png)

One of the oldest of these patterns is to have **Software 1.0** remain in control of the overall system flow while calling out to a **Software 2.0** machine learning model to perform a narrow task that would otherwise be too difficult to implement with traditional software, such as machine vision. The system around it is still procedural and deterministic, but it hands off one narrow part of the problem to a machine learning model. Code provides the structure, while the model provides the inference.

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*JrAHddE3zOkylItnmdk08Q.png)

Flipping things around, you can have a **Software 2.0** model in the driver’s seat, in this case quite literally. This is the direction autonomous vehicles have adopted, with a machine learning model receiving input from various sensors and producing output signals that traditional software uses to handle tasks such as steering, braking, and acceleration.

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*pna8j_aXqJnpXDtdGPFCQA.png)

In a similar vein to invoking a **Software 2.0** model from a **Software 1.0** system, a **Software 1.0** system can also invoke **Software 3.0** capabilities within a deterministic workflow. In this case, the cognitive power of an LLM is employed to perform a task inside an otherwise procedural flow. Unlike a narrower machine learning model, the LLM can take on a wide range of responsibilities depending on the system prompt and the input it is given, which may itself be multimodal, including images or documents. While the response may be freeform text, it can also be constrained to conform to a JSON schema. This gives traditional software systems powerful new cognitive capabilities while still remaining firmly in the world of workflows rather than agents.

## The World of Agents

With **Software 3.0** we cross an important threshold. In the patterns up to this point, the system may have employed a learned model or an LLM, but the overall flow remained procedural. Once the LLM is in control, that changes. You give up determinism, *but that is also the point.* Rather than explicitly laying out the full sequence of steps, you specify a goal and allow the system to work toward it.

That is the real programming model here. A **Software 1.0** system is programmed with code. A **Software 2.0** system is programmed through data and optimization. A **Software 3.0** system is programmed through natural language. You describe the task in English, provide the right context, and equip the system with the right capabilities. From there, it can often carry out surprisingly capable work.

Most people are already familiar with this pattern through products like ChatGPT, Claude, and Gemini. Even in a simple case like web search, the combination is powerful. A user describes a goal in natural language, the system decides what information it needs, retrieves it, and synthesizes a useful result. That alone is enough to show why agentic systems matter. But for builders, the more interesting question is what happens when you start wiring your own tools, models, and systems in behind that interface.

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*5Fu6rYt4rj2BPxKxuub21A.png)

The simplest form of an agentic system is a **Software 3.0** system connected to **Software 1.0** tools. These tools might be search, data retrieval, APIs, databases, or internal services. The important shift is that the LLM is no longer just producing an answer. It is choosing actions. It is deciding which tools to use, in what order, and how to use the results to make progress toward a goal.

This is what makes the pattern powerful, but it is also what introduces the tradeoff. A workflow can be carefully specified ahead of time. An agent cannot. Its behavior is shaped through natural language, context, and the capabilities it is given, which makes it far more flexible, but also fundamentally non-deterministic. That flexibility is often worth it. It is what allows a system to handle messy, open-ended tasks that would be difficult to reduce to a fixed sequence of steps.

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*zIB1Ereh19bqL4bmrD5JkA.png)

Once **Software 3.0** is in control, there is no reason to limit it to **Software 1.0** tools alone. It can just as easily call into systems built with any of the other paradigms. A tool might be a traditional API written in code, a narrow Software 2.0 model trained for a specialized inference task, or even another Software 3.0 system serving as a subagent.

That is the main point of this pattern. When **Software 3.0** is in the driver’s seat, everything else in the stack becomes a capability it can draw upon. Traditional software still matters. Narrow learned models still matter. Other LLM-based systems are shoulders for an agent to stand on. The agent does not replace them. It composes them. This is where the architecture starts to become more interesting, because the challenge is no longer just building individual components. It is deciding which capabilities to expose, how much autonomy to grant, and where the boundaries of control should sit.

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*2nV2X_fF2S5sI-JQTED5sg.png)

There is one further step beyond giving an agent a fixed toolbox. Instead of only allowing it to choose from predefined capabilities, you can allow it to write and execute code of its own. This is a distinct pattern, and an important one. The point is not that the agent is creating software as an end in itself. The point is that it can generate **Software 1.0** on demand in order to solve the task in front of it, then dispose of that temporary software once the task is complete.

That matters because a fixed set of tools, whether exposed through MCP or any other interface, is fundamentally limiting. An agent can only do what its existing tools allow. Once it can write and run code, it can build its own tools in the moment. It can analyze datasets, transform files, generate visualizations, create presentations, automate one-off tasks, and generally perform work that would be awkward at best, and often impossible, to package ahead of time as a static interface.

This is one of the most powerful patterns now emerging in systems like OpenClaw. It is also one of the most consequential. Giving a frontier model the ability to execute arbitrary code is not a small extension of tool use. It is a real increase in power. That power can be incredibly useful, but it also raises the stakes around permissions, isolation, monitoring, and trust. An agent with a simple toolbox can be helpful. An agent that can build its own tools can do real work.

## Conclusion

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*eVcjGX4iOsJ-JByMhUVTRA.png)

The future of software is not **Software 1.0**, **2.0**, or **3.0** in isolation, but the combination of all three. Code still provides structure, learned models still provide specialized inference, and language now provides a new interface for directing intelligence itself. The important question is no longer which paradigm wins, but which one is in control, and how the others are composed around it.
